# Built-in quota recovery

## Register before spending the window

Use the Codex app's discovered `automation_update` tool. The default is a heartbeat attached to the current task, local execution, recurring every ten minutes. It is not a standalone cron, another project run, a polling subagent or a sleeping shell. Use the live schema for the recurrence representation; do not hand-write app directives or edit automation TOML to create/update a schedule. Do not add a model override to a heartbeat when the schema does not support it. The host model checks and then delegates real work as usual.

Discover before creating. First view the checkpoint's saved monitor ID if present. If it is missing, stale or the previous create response was interrupted, inspect the existing local automation metadata using the app's supported discovery method (currently read-only inspection of `$CODEX_HOME/automations/*/automation.toml`). Match both a stable mission ID and the original task ID in the saved prompt; names alone are insufficient. Reuse the matching schedule, including a paused one only after an explicit mission resume. If ambiguity remains, resolve it instead of adding another schedule. Never change an unrelated automation. Preserve existing fields, including notification preferences, when updating.

Create with a clear name such as `Goal Router — <short mission name>`, destination current task, an ACTIVE recurring ten-minute schedule and the concrete prompt below. Fill in real identities and canonical file paths. If current task identity cannot be obtained reliably, use the tool's current-task binding and its returned identity; never invent an ID. Save the returned automation ID, effective cadence, task association and active state before claiming success. View the record when the create/update response does not confirm those facts. An uncertain write is an uncertain monitor, not permission to create a duplicate.

If tool access or recurrence support is absent, or registration fails, save `monitor.status=unavailable` and explain once that automatic recovery is not enabled. Continue authorized foreground work. No OS scheduler, external service or raw configuration workaround is part of this skill.

## Saved prompt

Use the following prose as a template. Replace bracketed fields; do not save unresolved placeholders. Keep it small. Do not include source files, logs, secrets or the full brief.

> Follow up on Goal Router mission [mission ID] in this original task [task ID]. The canonical mission is [mission path], the checkpoint is [state path], and the recovery instructions are [installed skill path]/references/heartbeat.md. Perform a minimal check in the current coordinator; do not delegate the check or scan the repository. Respect the latest user instructions and the original authorization boundaries. If the mission is verified complete, cancelled, deliberately paused, or waiting for required user input or authorization, stop this mission's monitor through the built-in automation tool and retain the checkpoint. If useful work or a worker process is still running, leave it alone. Otherwise establish the latest work run and its actual interruption reason. If the stop cannot be classified or bound to this work attempt, record a blocker, report the required attention once and stop the monitor. Only a confirmed quota interruption with fresh usable quota and no intervening user stop permits automatic continuation. Read current usage through the supported tool; unknown usage is not available usage, and both short and weekly limits can matter. When quota is still unavailable or unknown, retain the recurring schedule and end this check. When recovery is justified, inspect the partial artifacts and relevant processes, preserve valid evidence and completed decisions, and continue the next unfinished authorized slice with $goal-router in this same task. Never restart the whole mission, redeem reset credits, change the root model, create another task or repeat external side effects. Record progress at safe boundaries. Stay quiet while state is unchanged or non-actionable; notify only on meaningful recovery, completion, a monitor failure or required user action. Keep the single recurring monitor until the stopping condition is met.

Notifications belong in this prompt's meaning, not periodic status spam. Do not add a message every ten minutes. Use the platform notification setting only if the user asks to mute notifications; preserve it on updates.

## Each wake

Read the small checkpoint and latest task status first, plus any newer user instructions. An old `active` checkpoint is not proof that work still runs: quota can terminate the model before it saves a new status. Conversely, the current heartbeat turn being active is not proof that the earlier work still runs. Check the actual previous work/worker/process state, excluding this check. Do not dispatch any new work while a previous writer may still be active. If runtime status is unavailable, classify conservatively rather than infer idleness from elapsed time.

Bind the interruption evidence to the latest work attempt. Use the runtime's recorded quota error/status, and capture the associated run identity in the checkpoint when possible. A generic tool error, stale quota_wait note, long silence, or low remaining quota alone does not prove this interruption was caused by quota. If a stop cannot be classified, report the required attention once, save a non-quota blocker and stop the monitor. Do not automatically override a later user stop with an older quota failure.

Use `get_usage_limits` when exposed. Its `usedPercent` is consumed usage; `resetsAt` is a Unix timestamp in seconds. Prefer the applicable `rateLimitsByLimitId` bucket over the legacy single bucket. Know which bucket applies to the coordinator; do not treat any other model's available quota as proof that this model can run. Examine all returned limiting windows, including the weekly one, plus explicit account/spend restrictions. Do not save the account ID, credits balance or full response in the skill package or progress log. Retain only necessary status and recovery time in the mission state. `scripts/recovery.py` contains a read-only normalizer and decision helper for runtime-collected facts.

Fresh means just read during this check; the helper tolerates at most two minutes. The normalizer requires both windows to have readable percentages, or an explicit current `ordinaryUsageAllowed=true` for the ordinary `codex` bucket alongside its readable non-exhausted window. A null/missing window is otherwise unknown, not a zero-use window. Do not assume quota is restored merely because a saved reset timestamp has passed. Do not spend reset credits or buy credits. If the usage tool is missing or inconclusive, leave the schedule intact and report the monitoring limitation once; do not declare quota restored. Repeated unchanged waits remain quiet.

When quota is available, reconcile before resuming. Re-read permission boundaries, inspect the slice's partial diff and active processes, and reuse evidence whose dependencies did not materially drift. Do not rerun an uncertain irreversible action; inspect its result or leave it for the required confirmation. Return to the interrupted slice's next unverified step, not to intake. Register a fresh work-attempt identity before dispatch, so later quota evidence cannot be mistaken for the previous run. Keep the same existing monitor; do not reset its ten-minute cadence after each recovery.

## Shutdown and limits

Use the supported automation update operation to pause/disable the matched monitor after completion or deliberate stop. Preserve its fields and record the result. This is pausing a schedule, not pausing a native Codex goal. If shutdown fails, leave the terminal mission state in place so future ticks remain no-ops, and notify the user of the schedule failure. On explicit user resume, reuse/reactivate the monitor and continue the saved mission.

The machine and application must be running with access to the project. The heartbeat itself uses model quota and existing task context. A successful wake may consume usage; no claim of negligible cost is justified without measurement. At most 144 scheduled opportunities occur in 24 hours at a ten-minute cadence, not necessarily 144 successful model runs.

If a tick is too early, the recurring schedule already includes the next tick; no model call is needed to *request* that next recurrence. Whether the platform actually keeps retrying after a quota-related run failure, catches up after sleep, or starts a turn after a native goal budget stop must be verified in that environment. Do not promise a ten-minute recovery SLA. The local simulations assume the scheduler remains active; they do not establish platform behavior.
