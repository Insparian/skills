# Goal Router

Keep one mission and its original verification standard. Optimize total cost per accepted outcome: execution, coordinator calls, repeated context, repairs, reviews and recovery all count. A cheaper first attempt can cost more after rework. Model mappings live in [config/roles.json](config/roles.json); the recommended coordinator uses the SENIOR model and effort. Coordinator and executor are responsibilities, not model identities.

## Establish the mission and launch

Read the approved brief, applicable project rules and one compact checkpoint. Preserve the goal, completion criteria, authorized and forbidden actions, external boundaries, assumptions and stop conditions. Reuse existing project state; a missing repository map or checkpoint reconstruction goes to an execution worker. Intake does not require reading the full history, source tree or broad diffs. Follow [state-and-resume.md](references/state-and-resume.md) when establishing or reconciling state.

Before long execution, establish the actual coordinator model and effort from reliable runtime evidence or the user's current model selection. Defaults and guesses are not evidence. Before guard activation, run `scripts/route.py <features.json> --launch <launch.json>` with the small launch record described in [routing-policy.md](references/routing-policy.md). Missing or non-recommended identity returns a launch gate before any route. Ask once for the current selection or the user's explicit choice to proceed unverified. Do not switch models, create a child coordinator, or repeatedly ask after a confirmed unchanged selection. An explicit unverified choice permits continuation with `allow_unverified=true`; report it as such. A confirmed launch still does not establish quota savings. Record the applicable quota bucket when known; otherwise retain unknown.

After bounded intake, activate a reviewed project-local guard if available. Follow [coordinator-boundary.md](references/coordinator-boundary.md). It restricts the coordinator regardless of model and exempts only positively identified worker turns. Report active, unconfirmed or unavailable status honestly; missing lifecycle identity is a compatibility limit, not permission to infer worker identity from a model name. Never overwrite existing hooks or policies without review.

Before long work, establish or reuse one recurring thirty-minute heartbeat in this original task, following [heartbeat.md](references/heartbeat.md). This preserves the accepted quota-recovery behavior. No polling subagent, cron workaround or external scheduler. Only announce recovery as enabled after tool confirmation. If unavailable, report once and continue authorized foreground work with checkpoints.

Briefly announce launch status, chosen execution owner, any justified independent review, monitor status and guard status in the user's language. This invocation does not authorize scope expansion, uploads, deployment, reset credits or another task.

## Execute cohesive outcomes

Use [routing-policy.md](references/routing-policy.md) and its deterministic helper with verified features. It classifies supplied facts; it does not discover the model, understand the repository or enforce delegation. After guard activation, any helper execution belongs to the current worker, including route proposals and usage summaries; the coordinator chooses from returned results without running shell tools. Do not spawn a separate worker merely for a helper call. Have a worker map the relevant entry points, baselines, gaps and dependency-ordered outcomes, returning compressed evidence. Read [phase-contracts.md](references/phase-contracts.md) only when forming those outcomes.

Keep one execution owner for a cohesive slice through implementation, targeted verification and ordinary repairs. WORKHORSE handles ordinary work. SENIOR can execute deep or ambiguous cross-module work and interacting identity, provenance or state-transition invariants directly. Establish invariants and adversarial counterexamples before implementing those flows. Choose capability from expected completion cost and concrete failure evidence, not task volume or the lowest per-token price. MECHANICAL is useful for an independent deterministic slice; do not create a separate verifier merely to rerun commands the owner already evidenced.

Delegate with [context-capsule.md](references/context-capsule.md): original criteria and boundaries, current evidence, allowed paths, dependencies, outcome, validation and stop condition. Use fresh/no-history context where supported. Profiles require installation; otherwise use supported explicit model/effort overrides and the profile's instructions without conflicting full-history inheritance. Report the actual fallback when capability is unavailable; never pretend a worker used another model. Workers do not create nested coordinators or schedules.

The coordinator selects outcomes and integrates concise evidence; it does not reproduce repository labor. Workers return changed paths, exact command outcomes, criterion coverage and unresolved dependencies. Missing evidence returns to the owner. Independent review is justified by consequential architecture, security/privacy, release, irreversible migration or adversarial correctness questions. FRONTIER receives a bounded question and compressed evidence after reconnaissance, returns findings or a decision, and leaves repair to an execution owner. Preserve valid reviews; changed dependencies require review of the affected boundary. Zero to three frontier passes is a review target, not a savings metric; further passes need a recorded reason.

Default to one active worker. A second requires an explicit user preference for wall-clock speed, independent outcomes, neither FRONTIER and at most one writer. FRONTIER runs alone. Use the longest practical interruptible wait supported by the host; avoid ten-second polling and status requests while nothing needs a decision. Batch worker updates at blockers, decisions and completed outcomes while preserving required user-facing updates.

After one failed repair, reconsider the underlying cause. Two attempts without new evidence require reclassification or a justified capability escalation. A demonstrated WORKHORSE reasoning failure may transfer the intact slice to a SENIOR executor. Missing credentials, authorization, environment or product decisions remain prerequisites. Do not weaken tests or repeat unaffected suites to make a route look successful.

For local accounting and matched comparisons, use [completion-cost.md](references/completion-cost.md) and `scripts/usage.py`. Include coordinator, workers, retries and review. Unknown usage stays unknown; cached input and reasoning output are subsets. Keep private runtime samples outside this package. No savings claim follows from role counts, simulated tests or unweighted token totals.

## Recover and finish

Checkpoint before dispatch and after verified progress. On a scheduled wake use the bounded flow in [heartbeat.md](references/heartbeat.md), excluding the wake itself from active-work detection. Resume only a confirmed latest-run quota interruption with fresh applicable quota, intact authorization and no active writer. Reconcile partial artifacts and uncertain side effects through a worker before continuing the unfinished slice. Reuse completed decisions and passing evidence whose dependencies remain valid. Unknown stops, user pauses and permission gates do not auto-resume. Honor an already-active native goal; do not create one without explicit user request.

At the final gate, obtain the original criterion-to-evidence matrix from the execution owner or an independently justified verifier. Compare every original criterion without reopening broad product diffs or rerunning all tests. Distinguish complete, incomplete, blocked, awaiting authorization and real-world validation. Offline results do not establish production approval. Stop and verify monitor shutdown on completion, deliberate pause/cancellation or a non-quota blocker needing user input. Report outcomes, evidence, remaining boundaries, launch/fallback limitations and measured usage coverage concisely. See [compatibility.md](references/compatibility.md) for installation and platform limits.
